# Internationalization conventions

ParcelHub uses `i18next` with `react-i18next`. English (`en`) is the source and
fallback locale. Locale resources live in `client/src/i18n/locales`.

On a first visit, the browser language selects the best supported locale. An
explicit selection in the language switcher is stored for one year in the
`parcelhub.language` cookie and takes precedence on later visits. Supported
languages use their lowercase ISO 639-1 codes: `en`, `zh`, `ja`, `fr`, and
`de`.

## Translation-key naming

- Use lower camel case and dot-separated, semantic segments.
- Start with the owning feature: `dashboard.metrics.totalPackages`.
- Put genuinely shared concepts under `common`: `common.actions.signOut`.
- Name a key for its meaning, not its English copy or screen position. Prefer
  `pickup.confirmation.title`; avoid `confirmPickup`, `greenBannerText`, or
  `package_collected`.
- Keep related variants together: `common.roles.admin` and
  `common.roles.user`.
- Use i18next interpolation instead of concatenating translated fragments:
  `welcomeMessage: "Welcome, {{name}}"`.
- Use i18next plural suffixes (`_one`, `_other`, and any locale-specific forms)
  and call the unsuffixed key with `count`.
- Do not reuse a key only because two English strings currently match. Share a
  key only when the underlying concept is also the same.

Examples:

```ts
t("common.status.loading");
t("dashboard.awaitingPickup.packageCount", { count });
t("recipients.form.email.label");
t("recipients.form.email.validation.invalid");
```

## Resource organization

The default `translation` namespace is intentionally sufficient for the
current application size. Top-level feature scopes keep ownership clear.
Introduce another namespace only when it becomes a useful loading or ownership
boundary, not simply to shorten keys.

When adding a locale, mirror the full English resource shape and register it in
`client/src/i18n/resources.ts`. TypeScript derives valid keys from the English
resource, so typos and missing key paths fail the client build.

Dates, times, and numbers should use the active `i18n.language` with `Intl` (or
i18next formatters) rather than calling locale methods without a locale.
